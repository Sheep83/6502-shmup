## 2. Memory map, and the chosen terrain-charset address

### The problem

The VIC can only take a charset from a 2 KB-aligned window inside its bank, and
**every one of the eight windows in bank 0 was already occupied**:

| window | held | |
|---|---|---|
| `$0000` | screen A at `$0400` | taken |
| `$0800` | the `main` code segment | taken |
| `$1000` | **character ROM shadow** | the VIC cannot see RAM here at all |
| `$1800` | same ROM shadow | — |
| `$2000` | diagnostic sprites, P5 ring tables | taken |
| `$2800` | screen B, raster executor | taken |
| `$3000` | HUD / player / enemy sprite bitmaps | taken |
| `$3800` | the blank aperture charset | must stay |

The old game put its charset at `$3800`. That address is where this engine's
**blank aperture charset** lives, and the aperture is the whole clipping
mechanism — so the old address was never available.

### The choice

**`$0800`**, freed by moving the `main` segment out of VIC bank 0 to `$5000`.

That is not a workaround; it is the pattern the engine already follows. The
player (`$4000`), scroller (`$4200`), weapon (`$4600`), object pool (`$4800`),
enemy (`$4900`) and collision (`$4c00`) are all main-thread code living outside
bank 0 so bank 0 can hold what the VIC must see. `main.asm` is main-thread code
too — `entry`, `mainLoop`, `gameFrame`, `gameInit` and the diagnostic HUD, with
no interrupt handler anywhere in it — so it belonged out there already.

Glyph code base **96 is kept from the old game deliberately**, so the metatile
definitions keep their literal character codes and `stage_map.asm` stays
byte-identical rather than being rebased by a transform nobody can eyeball.
Codes 96..167 land at `$0b00..$0d3f`.

**The unused parts of the window are blank by construction, not by a clearing
loop.** KickAssembler emits one contiguous PRG and zero-fills every byte no
segment wrote, so codes 0..95 and 168..255 load as zeros and render as `$d021`.
Verified in the PRG: `$0a00` and `$0d40` are zeros. The only non-zero non-glyph
bytes are the twelve-byte BASIC stub at `$0801` (character codes 0 and 1), and
`terrainInit` zeroes them.

### Current map

```
$0400-$07ff  screen A                  $4000-$415f  player code
$0801-$080d  BASIC stub                $4200-$440d  scroller
$0b00-$0d3f  TERRAIN GLYPHS (72)       $4600-$4756  weapon code
$1000-$1ed6  code (ROM shadow to VIC)  $4800-$48be  object pool
$2000-$23ff  diagnostic sprites        $4900-$4a4c  enemy code
$2400-$27ff  p5 ring tables            $4c00-$4cd7  collision
$2800-$2bff  screen B                  $4e00-$4ef6  p5 ring
$2c00-$3052  raster executor           $5000-$552d  main  (moved out of bank 0)
$3200-$357f  HUD sprite bitmaps        $5800-$5e39  terrain map data
$3580-$363f  player sprite bitmaps     $6400-$67ff  terrain sub-row tables
$3640-$3693  enemy sprite bitmap       $6800-$693f  terrain code
$3800-$3fff  BLANK aperture charset    $6c00-$6c0f  terrain state
                                       $c000-$cfda  module state / fixtures
```

`$d018` values, all four derived and asserted in the tests:

| | screen | charset | value |
|---|---|---|---|
| `D018_A` | `$0400` | `$0800` terrain | `$12` |
| `D018_B` | `$2800` | `$0800` terrain | `$a2` |
| `D018_A_BLANK` | `$0400` | `$3800` blank | `$1e` |
| `D018_B_BLANK` | `$2800` | `$3800` blank | `$ae` |

**The screen-page bits are preserved across the aperture switch**: only the
charset bits differ between a value and its blank partner. Asserted.

Assembler-time guards were added for: 2 KB alignment, the window lying inside
bank 0, the terrain and blank charsets differing, the glyphs fitting the window
and clearing the BASIC stub, the map data and tile tables fitting their
segments, the terrain state fitting its segment, and the sub-row table stride.

**The map data lives outside VIC bank 0** (`$5800`). The VIC never reads it —
only the character codes derived from it reach a screen page — so spending the
scarcest memory in the machine on it would have been wasteful.

## 3. Stage-row / world-progress mapping

Traced before any code changed, and the two engines turn out to agree exactly.

**The old game** (`shooter_test/src/main.asm:770-782`):

> `STAGE_START_ROW = STAGE_LOGICAL_ROWS - 23` (bottom origin) … "The existing
> coarse-scroll decrement then walks the viewport upward (`SCROLL_ROW--`)
> through the whole authored level to logical row 0, and only then wraps
> 0 → `STAGE_LOGICAL_ROWS-1`."

**This engine** (Slice A′): `STAGE_START_ROW = STAGE_ROWS - SCREEN_ROWS`,
`stageTopRow` decreasing to 0 then wrapping, `worldProgress` only increasing.

Identical semantics. The only difference is aperture geometry — the old game
showed 23 rows, this one 25. **No data reversal was needed and none was done.**
Authored row 419 is the bottom of the level and is shown first; authored row 0
is the top and is reached last.

```
screen row r  shows  stage row  (stageTopRow + r) mod STAGE_ROWS
stage row     ->     metatile row = row / 4,  sub-row = row mod 4
metatile ID   =      stageMetatileRows[metatileRow * 10 + col]
character     =      metatileDefs[id * 16 + subRow * 4 + i]
```

`STAGE_ROWS` is now **derived**, not restated: `STAGE_METATILE_ROWS (105) ×
METATILE_H (4) = 420`. That it equals the placeholder height Slice A′ picked is
luck; that it is derived is not, and a guard fails the build if a future level
disagrees with the scroller that walks it.

## 4. Real terrain regeneration design

**The engine's existing schedule was already the right shape and was kept.**
`regenTick` rebuilds the hidden page a few rows at a time across the frames
between coarse steps; `renderRow` sets `scrPtr` at the row and
`renderBackgroundRow` reduces the stage row mod `STAGE_ROWS`. Only the drawing
changed — `renderBackgroundRow` now ends in `jmp renderTerrainRow`. No burst
renderer was introduced and no job system was built.

Two things were done to make the real decode affordable:

**Transposed sub-row tables.** `metatileDefs` is row-major 4×4, so a stage row
needs four consecutive bytes at `id*16 + subRow`. Decoding that directly needs a
16-bit pointer per metatile (`id*16` reaches 544), and then the def read and the
screen write want *different* index registers — the def index runs 0..3 while
the screen index runs col..col+3. Biasing a pointer to make one register serve
both costs another 14 cycles per metatile. Measured on paper at ~1,040 cycles a
row, which would have made real terrain 30% dearer than the placeholder.

So the defs are transposed **once, at init**, into four tables 256 bytes apart:

```
trTiles[subRow*256 + id*4 + i]  ==  metatileDefs[id*16 + subRow*4 + i]
```

`id*4` is at most 135, so the def read becomes `lda abs,X` with a one-byte index
and the screen write stays `sta (scrPtr),Y`. The two indices advance
independently and no pointer arithmetic survives the inner loop. The tables are
page-aligned so selecting a sub-row patches four *high bytes* at the top of a
row rather than eight. **The authored file is not rewritten** — the transpose
happens at run time, so `stage_map.asm` stays diffable against the original.

**A metatile-ID cache.** A metatile is four character rows tall, so
regenerating a page walks four consecutive stage rows out of every metatile
row, and all four want the same ten IDs. Re-reading them costs a 16-bit
multiply, a pointer build and ten indirect loads — about 200 cycles — for an
answer unchanged three times in four. The cache is keyed on the metatile row
alone, so it stays valid across a page flip.

Together these took a row from **1,158 to 898 cycles**.

**`ROWS_PER_TICK` was lowered from 5 to 4.** The scroller's own comment said the
headroom was real and available but that P4 "has no measurement that needs it".
This slice had one: a real row costs more than a placeholder row, and the peak
is what collides with a dense sprite frame. Four rows finishes 25 rows in seven
of the eight frames between coarse steps — one frame of margin instead of three
— and `scrollLate`, the counter that says whether that margin is enough, is
measured at zero.

## 5. Colour RAM and the VIC colour registers

The level's own generated header settles it: *"Terrain colour is level-global;
there is intentionally no per-cell colour table."*

So **colour RAM is written once, at init, and never again**. That is also the
only thing that could be correct: colour RAM is not double-buffered — there is
one `$d800` for both screen pages — so a per-cell colour would have needed a
second copy the VIC cannot give us.

This is the single biggest reason the real terrain is affordable: regenerating a
row writes **40 bytes of screen RAM and zero bytes of colour RAM**.

| register | value | role |
|---|---|---|
| colour RAM | `9` = `8 \| 1` | bit 3 selects multicolour; low 3 bits are bit-pair 11 |
| `$d021` | 12 | bit pair 00 |
| `$d022` | 15 | bit pair 01 |
| `$d023` | 11 | bit pair 10 |
| `$d016` | bit 4 set | multicolour **text** mode |

`$d016` is read-modify-written, because it also carries CSEL and XSCROLL and
this engine scrolls vertically through `$d011`. The old game set MCM the same
way and for the same reason.

`initColour` is gone; `terrainInit` owns the playfield's colour, and owning it
in one place is what stops the two disagreeing.

**One visible change the user should expect:** `$d021` was 0 (black) and is now
12 (medium grey), because that is what the level authors. The area above and
below the terrain, inside the open border, will be grey rather than black.

## 7. Focused tests added

**`tests/test_terrain.py`** — new, in `make test`, with `make test-terrain`:

- the level package is byte-identical to the reference checkout;
- the format matches what the decoder assumes, and every ID in the map resolves;
- every character the level can emit is inside the glyph namespace;
- four consecutive stage rows reproduce one metatile's 4×4 cell;
- the stage-row → metatile-row / sub-row split, at the boundaries;
- all 420 rows expand to 40 codes;
- addresses are disjoint and the four `$d018` values are *derived*, not restated;
- terrain owns no gameplay VIC state;
- the 6502 fills a row with exactly the model's codes, for eight stage rows;
- **screen A and screen B produce identical content** for the same stage row;
- colour RAM is the level's single colour (masked to 4 bits — it is a 4-bit
  register and reads back as `$c9`, the same trap Slice A hit with `$d027`);
- the aperture selects the blank charset above the band and the terrain charset
  inside it, sampled **by raster** because which value is live depends entirely
  on where the beam is;
- after two seconds neither page holds a code outside the glyph namespace.

**`tests/test_slice_a_prime.py`** — updated, because the terrain contract
invalidated how it identified a row:

- a row was identified by the two hex digits the *placeholder* wrote in columns
  0-1. It is now compared against all **forty** character codes the level says
  it should hold — strictly stronger, and it fails for the same reasons.
- "no two adjacent rows are identical" was removed: real terrain repeats
  (metatile M0 is forty identical characters on all four sub-rows), so that
  assertion fails on *correct* output. What it was *for* — catching a mirrored
  page — is now tested directly against the reversed expectation.
- `STAGE_ROWS` is checked as derived, and its value against the real map.
- the snapshot is retried until the displayed page's stamp has settled. The
  scroller documents a one-frame window between the software flip and the IRQ
  adopting it at raster 250, and the test was landing in it; it now fails
  loudly only if the two never agree.

## 8. Performance measurements

Cycle-exact, VICE monitor stopwatch. "Pure" = raster IRQ masked at `$d01a`
around a direct call; "elapsed" includes the interrupts that land inside.

### Terrain regeneration

| | cycles |
|---|---:|
| `renderTerrainRow`, one row, pure (min / med / max of 9) | 855 / **898** / 941 |
| before the ID cache | 1,072 / 1,158 / 1,201 |
| `regenTick`, working frame, pure (4 rows) | ~3,592, worst sample 4,494 |
| `regenTick`, working frame, **elapsed** (med / max of 40 frames) | 5,716 / 6,023 |
| `regenTick`, idle frame | 15 pure, 21 elapsed |
| `terrainInit`, **once at boot** | 17,362 |

**The placeholder cost ~3,941 cycles on a working frame** (5 rows × ~788, from
the capacity audit). The real terrain costs **~3,592** — it is *cheaper* per
working frame than the diagnostic pattern it replaced, while drawing the actual
level.

**Regeneration is spread, not bursty:** over 40 sampled frames, 35 regenerate
and 5 are idle — four rows on seven of every eight frames, which is the
coarse-step cadence.

### Main-thread health, 3-second free runs

| load | span (lines) | overrun | spanOver | publishSkip | schedDefer | scrollLate |
|---|---:|---:|---:|---:|---:|---:|
| no enemies | 152 | 0 | 0 | 0 | 0 | 0 |
| 4 enemies, spawner live | 191 | 0 | 0 | 0 | 0 | 0 |
| 4 enemies + firing | 215 | 0 | 0 | 0 | 0 | 0 |

Of the PAL frame's 312 lines, the worst measured main-thread span with a
representative enemy load and the gun firing is 215 — roughly 13,500 of 19,656
cycles. **No overrun, no publication skip, and no late back page.**

### A finding, recorded rather than chased

Between the first terrain implementation and the optimised one, the Slice C
ladder at **16 well-separated enemies** reported one frame-record publication
skip per three-second window, reproducibly (2 of 3 runs). That is the regime the
Slice D advisory and the capacity audit already document as beyond the
sustainable ceiling — the audit put it at about eight well-separated sprites.
After the transpose and the ID cache the whole gate is clean, including that
ladder. It is noted because the margin there is genuinely thin, and terrain is
now spending some of it.

## 11. Turrets, waves and the editor ABI were not migrated

**Explicitly not done**, as instructed.

- **Turrets.** `stage_turrets.asm` was not copied. Nothing is rendered, no
  collision, no colour pulse, no sprite reserved. **Turret markers are not
  embedded in the terrain data** — the old game keeps placement in its own file
  as two assembler lists, `turretCols` and `turretRows` (8 turrets), with the
  mapping `world row = metatileRow * 4 + 1`, `world col = metatileCol * 4 + 1`.
  So terrain interpretation is clean, and the placement layer can be recovered
  later without disturbing anything here.
- **Waves.** `stage_waves.asm` was not copied.
- **The editor ABI.** The engine does not depend on the Python level editor. The
  generated files are consumed as data; regenerating them is a later concern.
- **Score, upgrades and lives** are untouched.
- Level 2 exists in the old repo and was ignored.
